# A tool's presentation is part of its definition and must be replay-pure

How a run's work presents on screen is declared once, where the tool is defined, next to its schema: a tool's `presentCall` and `presentResult` return a card union (`generic` / `terminal` / `diff` / `search`) that names what the tool does. For catalog tools the presenters sit on the `ToolDefinition` entry itself; for Pi Core's builtin loop tools — whose schemas live in the vendored package this app cannot annotate — one app-side module stands in as their definition site. Either way there is exactly one declaration per tool, written by whoever adds the tool; no central filename regex or title heuristic learns about it after the fact, because such a guesser is wrong precisely for the tools added after it was written, and every one of those guesses had to be maintained by hand.

Two properties bind implementations. Both presenters are pure functions of their inputs — they run live on streamed arguments and again later on the Turn Record replay, so any I/O, session read, clock, or randomness would render the same recorded call differently across replays; tool-call entries therefore record their arguments so replay has what the presenter needs. And they never throw: a malformed or older recorded argument returns `undefined` and degrades to a generic card, because display must never break replay — an unreadable old entry is a rendering constraint, not data loss.

The same declaration is what makes derived lists honest. Produced files come from diff cards and edit-declared locations — what tools say they mutate — so a file the model forgot to mention still appears, and a file a tool only read stays out. Presentation is UI-facing by definition: nothing a presenter returns may flow back into a model-visible result or into the record's account of what happened (ADR-0048 keeps those facts separated).
